## Decisions and deviations

### D1 — Databricks only; no Snowflake comparison

**Checked 2026-09-29.** `SHOW AVAILABLE LISTINGS` on our Snowflake trial (4,222
listings) has three FHIR listings, all by Kipi.bi. The closest, "Kipi Health Data
Utils - FHIR Synthetic Data" (`GZSTZ4CLE1N7D`), is a different product: Kipi's own
generator, "10K static data records" per entity, delivered as an installable app.
The Databricks listing is Synthea bundles published by Databricks.

Same standard, different data, so a platform comparison would compare two
datasets, not two platforms. **Decision (user, 2026-09-29): build on Databricks only.**

No listing named "FHIR R4 Read with SQL" exists on either marketplace; it is the
name of the notebook inside the Databricks listing.

### D2 — The data is synthetic

Synthea patients are generated, not real. Good for building and testing the
pipeline with zero privacy risk. Its numbers must **never** be presented as
real-world health facts: every report and chart says "synthetic".

## Known from the listing's notebook (to confirm on our own run)

- Medications appear in `medicationCodeableConcept`, not the standard `medication`
  field — the notebook's authors call this non-compliant.
- Only institutional (837I) and pharmacy claims; no professional claims (837P).
- Resources are linked by ids inside each bundle (e.g. a Claim's `patient`
  points to a Patient `id`); a broken link is a quarantine case.

### D3 — Static source; incremental loading is simulated

All 1,156 source files were last modified on 2022-04-15 and the listing has no
update frequency. Nothing new will arrive. To practise incremental loading (what
real FHIR feeds need), the files are loaded in batches. Recorded so no one reads
the batch runs as a live feed.

### D4 — Sample profile first (50 of 1,156 files)

Profiled 50 files spread by size (`docs/design/dataset_profile.md`). The largest
patients (to 39.6 MB) and the two reference files are not in the sample, so counts
there are not totals. The full profile needs the whole 2 GB: ~3.5 hours to download
at this laptop's measured speed, or run it inside Databricks instead.

### D5 — The Marketplace share contains no tables

**Checked 2026-09-29, after installing the listing.** Unity Catalog API: catalog
`databricks_fhir_r4_synthetic_data` is type `DELTASHARING_CATALOG`, share
`exchange_fhir_r4_synthetic_data`, status `INSTALLED` - and its only schema is the
automatic `information_schema`. The listing's content API lists one object: the
notebook "FHIR R4 Read with SQL". The data itself is the public S3 folder the
notebook reads.

**Consequence:** bronze reads the raw JSON bundles from that S3 folder, as the
listing's own notebook does. The shared catalog is left installed (no cost, no
data) and is not used by the pipeline.

### D6 — Databricks reads the public S3 source directly (tested 2026-09-29)

One-file test on the SQL warehouse, smallest source file (62 KB):
- Without options: `CF_FAILED_TO_INFER_SCHEMA` - the reader expects JSON Lines
  (one record per line); each FHIR file is one multi-line JSON object.
- With `multiLine => true`: readable. 1 row: `resourceType = Bundle`,
  `type = transaction`, `size(entry) = 29` - equal to the minimum records per
  patient the local profile measured (29).
- Detected columns: `entry` (array of structs holding every record), `resourceType`,
  `type`, `_rescued_data`.
- Timings: 16.9 s (first query, includes warehouse start), 10.4 s (second).

**Consequence:** no download or upload is needed. Bronze can read the source with
`multiLine` JSON, and the full profile can run inside Databricks.

### D7 — Full profile done inside Databricks (2026-09-29)

All 1,156 files profiled on the SQL warehouse, 188.8 s of queries; details in
`docs/design/dataset_profile.md` section 4. The first run failed on the
`address` shape conflict and its first two results were lost (the script saved
only at the end, 182.6 s wasted); fixed by saving after every query. Cost of
both runs: NOT MEASURED (Databricks billing not readable on this trial).
