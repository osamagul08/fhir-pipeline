1. Summary

  1. What: an automated Databricks pipeline that turns FHIR R4 — the world standard for exchanging medical records, as deeply nested JSON — into clean, linked, analysis-ready tables.
  2. Proven complete: all 1,156 source files and 631,630 records loaded; the counts of all 24 record types equal an independent profile of the source, measured before building.
  3. Proven incremental: loaded in 5 batches; each run processed only the new files (~2 minutes per batch, whatever the total).
  4. Quality enforced: automatic gates stop a run on lost records, duplicate ids, broken files or failed rules; problems are quarantined with a reason, never silently dropped. Final count: 0.
  5. Delivered: a 7-page, 55-chart Power BI dashboard, generated from code and kept in git.
  6. Not yet: production deployment, one automation Job, 13 smaller record types (section 7).

6. Findings worth knowing

F1 — Checks caught wrong assumptions before wrong numbers were published. A rule "every location has an identifier" stopped a run. The record was "Patient's Home" — a FHIR kind of place, not a specific address. The rule was corrected, and home visits (123 visits, 13 procedures) are now matched and labelled.

F2 — The same field has different shapes in different record types (an address is a list for patients, a single object for locations). Reading everything through one schema breaks; the pipeline gives each record type its own table and keeps the raw JSON in a flexible type.

F3 — Serverless jobs cannot reach the open internet. The file copy was switched to Databricks' built-in storage connector.

F4 — Auto Loader remembers file names, not contents. A renamed file would load twice; the gate now stops the run on duplicate ids, and the landing folder is treated as write-once.
